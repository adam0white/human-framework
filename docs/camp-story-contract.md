# Earned camp story 0.1.0 / save 1

The pure, synchronous `src/games/camp-story.js` selects camp host 0.2.0/save 2, Human 0.1.1 and clock 0.1.0. Original Common Ground and Before the rain remain unchanged. This is one actual camp followed by one finite authored supply window, not a replayed canonical opening or a universal campaign engine.

## Public interface

- `CAMP_STORY_VERSION = '0.1.0'`, `FERRY_MINUTES = 90`, `RAIN_MINUTES = 180`.
- `createGame(options = {})` starts the actual new camp; options are the kernel's `improvement` and `recovery` controls. This story always includes the neighbor.
- `migrateLegacyGame(snapshot, options = {})` explicitly validates/migrates the complete original Common Ground save through the new kernel. An established imported camp enters at its current minute; an unfinished one continues toward its own milestone. The kernel preserves the original source snapshot and declares its rest/assembly conversion. No original file is modified, historical cache timestamps invented, or missing command history reconstructed.
- `migrateLegacyRainGame(snapshot, options = {})` explicitly validates an original Before the rain save as an authoritative import prefix, migrates its actual world through the full camp kernel, and preserves its already opened window, deadlines, production, allocations, departure and ending. An old finished window stays finished. The new journal begins at import time; no missing old commands are invented.
- `startJob(game, id)`, `cancelJob(game)`, `requestProject(game, project)`, `releaseProject(game)`, and `requestHandover(game, from = 'player', to = 'neighbor')` forward to the selected kernel when work is running. Unilateral cancel/release remain available at checkpoints; these are explicit work commands, unlike reading/Continue.
- `advanceGame(game, minutes)` accepts 0–1440 whole minutes and stops at the next unacknowledged story boundary. `advanceToNextEvent(game)` uses the kernel's finite event/review boundary, clamped by the story. Pre-entry advancement checks each paid minute; all tied kernel completions and the neighbor's ordinary next choice settle before first-milestone entry.
- `continueStory(game)` acknowledges the supply introduction only. `allocateCache(game, 'households' | 'camp')` spends a distinct carried/new cache on one household kit or two camp nights. Each destination accepts two caches. `dispatchFerry(game)` closes the ferry at the inclusive departure checkpoint. `finishStory(game)` closes at rain, or after the actual ferry dispatch once both households and all four camp nights are covered. `returnToCamp(game)` leaves a finished window for ordinary continuing camp work, keeping its settled allocations/losses. Duplicate Continue, dispatch, finish and return reject.
- `getGameView(game)` is a detached kernel view with `phase` (`camp`, `introduction`, `packing`, `ferry`, `rain`, `ended`, `camp-return`), `window`, `enteredAt`, `ferryAt`, `rainAt`, `elapsed`, `remaining`, `ferryRemaining`, `availableCaches`, `carriedCaches`, `householdsEquipped`, `campNights`, `unprovidedHouseholds`, `unprovidedNights`, `departed`, `canFinish`, `canAdvance`, and `pauseReason`. `nextEventAt` is finite while advancing and null at a decision. Choice estimates include `finishesBeforeFerry` and `finishesBeforeRain`, both inclusive. A window field is null before entry; service counts are zero and unmet counts remain 2/4.
- `exportGame(game)` returns `{format:'human-camp-story',version:1,game}`. `restoreGame(snapshot)` rejects other save formats, version mismatch, invalid source worlds and inconsistent story derivations. Every call leaves its input untouched; returned game snapshots are deeply frozen to permit safe internal validation caching. No function calls an LLM, browser API, network or wall clock.

## One boundary, one supply record

At the first actual milestone, the entire selected-kernel world is captured unchanged as the authoritative entry snapshot. `enteredAt = world.clock.now`, `ferryAt = enteredAt + 90`, and `rainAt = enteredAt + 180`. The introduction is paused; acknowledging it pays no time and changes no actor, job, stock, skill or commitment. Entry rejects times that cannot represent both deadlines within the kernel's 1,000,000,000-minute limit.

The saved window contains entry/deadline facts, carried-cache count, actual post-entry completion receipts, distinct allocations, acknowledgment and departure/finish facts. Carried caches have aggregate ownership and numbered identities but no supposed birth times. New receipts are observed from paid kernel transitions and identify their actual completion minute. The kernel's cache counter remains cumulative; `availableCaches = world.caches - allocations.length`. Allocation changes ownership accounting in the wrapper and never reduces already-earned lifetime production counters or alters underlying people/work.

Completions at the ferry/rain minute settle before the checkpoint is presented. A cache completed exactly at the ferry is eligible for allocation before dispatch. This inclusive rule differs deliberately from Last Light's strict arrival deadline. Once dispatched, unmet household provision stays lost; later caches can still provision camp. At rain, unfinished work remains active. Finishing early is allowed only with all needs covered and the ferry actually dispatched at its checkpoint; it skips the remaining rain wait and does not simulate weather, night or travel. Before dispatch, allocated household kits are ready for the ferry; dispatch records kits sent, without inventing arrival across the water. Finishing at rain retains partial outcomes. Return resumes the same actual camp and cannot reopen this window.

## Snapshot authority and bounded replay

Before entry, the selected kernel's validated current snapshot is authoritative; no complete pre-entry command history is claimed. At entry, preserve one validated world snapshot as the root of a bounded window journal. Source code derives the window, receipts, allocations and current world by replaying that journal from this root. Import compares every derived field against the saved state, rejecting fabricated receipts/times, over-allocation, duplicate transitions and changed current worlds. Earned roots require the milestone at that exact minute; legacy continuation roots require the kernel's validated legacy provenance. Changing an internally consistent source snapshot is not detectable tampering and is not advertised as cryptographic history verification.

The finite window journal admits up to 1,024 ordinary commands, then reserves room for at most 180 paid one-minute advances plus cancellation/release and the four chapter controls. Consecutive advance commands coalesce, so chunk size does not change the canonical save. A hard 2,048-record bound applies before replay. Paid time cannot exceed 180 minutes before finish. Production receipts are bounded by the window's paid minutes and exact source replay; allocation count is at most four. After Return to camp the retained finite window proof stays frozen, while the continuing kernel again uses its current authoritative snapshot rather than an unbounded campaign journal. Its identity, options, origin and lifetime time/counters must extend the settled camp, and it cannot alter settled story facts. This establishes deterministic continuation from each snapshot, not recovery of unrecorded post-window commands.

Strict JSON traversal rejects accessors, cycles/shared references, excessive nodes/strings/depth and nonfinite numbers before cloning or replay. Caps reserve unilateral work controls and save access. Failed validation or admission never replaces the caller's current story. Private input fixtures and their provenance remain outside the public build.

## Acceptance evidence

Tests and source-bound evidence must cover earned build-first/stock-first entries, exact migrated busy gathering/rest and the actual minute-1,312 twelve-cache snapshot, all paid boundary ties, later camp benefit after a missed ferry, early surplus finish, ordinary return without window restart, owned meal/material carryover, forged journal/snapshot fields and driver parity. These are deterministic software checks; they do not establish human realism, attachment, a player-explanation gate or theological calibration.
