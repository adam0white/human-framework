## Alternative to decide first

A monorepo with existing origins and independent deployments captures shared tooling, dependency visibility and coordinated CI without migrating browser storage or combining security boundaries. It retains multiple host configurations and release pipelines. The proposed single origin simplifies the public URL and host configuration but adds migration, shared-origin exposure and whole-bundle deployment coupling. Neither benefit requires the other: measure operational savings and pilot costs before choosing the full target.

## Target and decisions

- One repo contains `games/<slug>/`, shared build tooling, a frozen pnpm lockfile, a registry mapping old origin, prefix, source SHA, build SHA, HF and lab versions, save schema and deployment status. Keep HF's source, central shelf and telemetry in their existing repo. Bring in each game with `git subtree` from a recorded exact ref, without squash if retaining original reachable commits is the objective. Verify original commit objects and history with `git log --follow` and `git merge-base --is-ancestor`; preserve original repos read-only during transition. Original signed commits retain their original objects and signatures; subtree merge/relocation commits are new and must be signed. Verify with `git verify-commit`, never claim relocated files were themselves signed by prior authors.
- Build each game with an explicit `/slug/` asset base, path-scoped routes and unique storage/cache names. Assemble to `dist/<slug>/`. Each `/slug/release.json` identifies game, monorepo SHA, source lineage, exact HF and lab versions, and `dirty:false`; validate every manifest against the exact deployed commit. One Worker deployment is atomic for the whole bundle: even unchanged games are redeployed. Build all outputs for deployment, or reuse immutable CI artifacts only when their source and dependency hashes are verified. CI path filters save game tests, not the need to prove the complete deployed bundle. Shared lockfile, shared tooling, HF/lab version and deployment changes trigger all affected games; a required aggregate job must fail if needed checks are skipped.
- Existing origins remain operational during the data migration window. Keep a redirect-exempt recovery page and migration bridge on every old origin for a retention period the owner explicitly sets; publish its direct URL and test an untouched browser profile returning after cutover. Traffic alone cannot prove all dormant clients migrated. Do not retire this recovery route without an explicit decision and a practical recovery alternative. A redirect cannot read old-origin localStorage, IndexedDB, Cache Storage or pending uploads and would strand them. Ship a versioned bridge on each old origin **before** redirect: explicit, origin-checked messages to a narrowly scoped new-origin receiver, with source/nonce validation, size limits, schema and replay validation, collision policy and idempotent acknowledgement. For large IndexedDB saves use bounded chunks or a user-selected export/import fallback, not URL parameters; never put save or identity data in URLs or logs. Preserve old data until verified at destination. Browser partitioning, CSP and unavailable old clients can block transfer; document manual export/import and retain old launch paths when transfer cannot be proved. Pending telemetry journal, feedback drafts, opt-out/consent and F-491 linkage need separate migration tests; do not silently opt people in or discard unsent notes. Confirm whether identity and shelf records remain central and whether receiver trusts `play` explicitly; test existing and new origins and denied origins.
- Inventory and namespace localStorage and IndexedDB, caches, and broadcast channels. A single origin means any same-origin game script can access every other game's storage; path prefixes are not security isolation. A compromised game has a larger blast radius. Preserve strict CSP per path and audit all third-party code; if that risk is unacceptable keep separate origins. Scope each service worker to `/slug/`, relocate script and precache paths, test upgrade/unregister of old workers, offline fallback and no cross-game interception. Changing DNS or issuing a redirect does not unregister a worker in an existing client.
- Per-game CSP, cross-origin lab connections, identity `frame-src`/`frame-ancestors`, analytics and cache policy must survive assembly. Check Worker asset header matching and 100-rule limit in a deployed preview; adjust the lab allowlist and identity message checks narrowly for `play`. Retain `static.cloudflareinsights.com`, `cloudflareinsights.com` and existing recording/privacy behavior. Test telemetry receipt, no-recording path, identity fallback and shelf carryover, not merely a network 2xx.

## Acceptance and cutover

The owner accepts the migration proposal and each production cutover. Before a pilot, agree measurable thresholds using the inventory baseline: every supported route and release manifest passes; replay, identity, consent, pending notes, CSP and offline checks pass; interrupted transfer is recoverable; and a returning untouched profile can reach the old-origin recovery page. Confirm a tested export or reconciliation path for progress made at the new origin before rollback. Record failed transfers and support cases, observe both for an owner-agreed period, and set explicit thresholds before any redirect or retirement. Traffic alone is insufficient. Until those thresholds and the recovery retention period are approved, retirement is not ready.

## Stages and stop/rollback points

Effort is a rough engineer estimate for one person, excludes external review, waiting for CI, and unknown game-specific failures; parallelism changes elapsed time, not total effort.

1. **Inventory and rehearsal (2–4 days).** Record exact live manifests and old URLs, source refs, repo sizes/history, licences, dependencies, built asset counts/sizes, route bases, service workers, data stores, CSP and live acceptance tests for every game. Verify DNS/Worker/account tier read-only, current holds, unique namespace and old-origin access. Rehearse subtree import and signature verification in a disposable local repository. Measure current CI time and build durations; define p95 build/CI and file-count headroom before cutover. **Stop** for conflicting ownership, missing histories or inaccessible data. Rollback: discard rehearsal only; no production changes.
2. **Create repo and CI (3–6 days).** After approval, import a low-risk representative game and preserve exact source. Establish pnpm workspace, common lockfile, full-build pipeline, per-game checks with aggregate status, signing and provenance. Compare original and imported replay outputs and baseline performance. Create preview-only Worker with test data. Rollback: abandon preview and repo branch; originals stay authoritative.
3. **Build migration bridge (4–8 days plus per-game work).** Build and independently review storage migration, collision handling, acknowledgement, idempotency, retained fallback and old/new client coexistence. Verify seed+input+state replay, large saves, interruption/retry, old and new identity, pending notes, consent, no-CSP errors, SW scope and offline behavior on actual supported browsers. Explicitly test interrupted copy, quota exceeded, blocked third-party storage, stale tabs and duplicate migrations. Rollback: keep old site authoritative; turn off bridge and keep both original and newly copied data. Do not delete or overwrite either copy.
4. **Pilot one game (2–4 days plus observation).** Publish old-origin bridge first, then deploy prefixed game to preview and production at `play`; compare UI, input, replay, telemetry and per-game release SHA. Route shelf to new game only after verified transfer and documented fallback. Use reversible temporary redirects only after the migration window; test deep links, query strings, status codes, offline caches and old SW behavior. Observe errors and recovery before making permanent redirects. Rollback: restore old shelf target and disable redirect; old origin remains usable. Any new-origin progress is a separate branch of data: provide export/reconciliation; do not assume reverse transfer or overwrite the old save.
5. **Migrate remaining games (estimate 1–3 days each, plus exceptions).** Repeat evidence and cutover per game. Separate central Watch/Voice/Well extraction from external games: their current code, cast, routing and release share `apps/site` and need explicit dependency separation. Preserve old hosts and the existing lab Worker. Do not migrate held games or override their qualification holds. For each game keep an owner, completed checklist and rollback receipt. Rollback per game via shelf and routing, retaining both data copies; a Worker rollback affects the entire bundle, so first verify other games' deployed versions and use an isolated emergency rebuild when a global rollback would regress them.
6. **Converge HF only after migration (unknown; potentially weeks).** Inventory exact live versions and frozen exports; port each game to one published version and pass native replay, performance, save, player and deployment gates. Child, Valley and Neighbours have explicitly unresolved performance/qualification gates in HANDOFF; they cannot be assumed to qualify. 4.x exact-engine saves may need fresh starts. Keep their working version and document exception until qualification; this is a dependency of the single-version target, not a reason to block the rest of repository consolidation. Rollback by reverting the affected game pin and build; preserve saves/exports from both versions.
7. **Retire old hosts only after evidence (1–2 days plus observation).** Measure bridge success and traffic; keep durable redirects, old history, privacy notice, and manual recovery path for a defined period. Decide retention from observed use, not a guessed deadline. Check all links, release manifests, analytics, CORS, cache headers and monitoring. Rollback: restore old origin deployments and shelf entries while retained; retirement must not delete source, saved exports or original repositories.

Each production change requires the repo's signed commits, lane checks, exact-head green CI and one clear hosted Codex review, then normal merge and deployment verification. Check the current coordination HOLD immediately before any merge. Confirm game-specific acceptance and the HF release lock before moving pins. User acceptance, live deployment, replay and migration success are distinct outcomes. The estimate is approximately 12–24 days for stages 1–4 and 7, plus 1–3 days per remaining game after the pilot, excluding HF qualification, reviews and observation; this is not a schedule commitment.
