**Test limits (none of these is a blocker):**
1. **Stale-driver setting.** The control runs the driver with `LAB_PLAY_ALLOW_STALE=1` (hold-control.mjs line 38). Because the fork lives in a folder with no git, players will probably need that same setting, or the driver will refuse to start. The director should set it when launching players.
2. **Release after the target disappears.** When the target is removed mid-hold, the page never sees the release on phone (vanish test: 4 downs, 3 ups). Release is shown indirectly: the next hold gets a fresh press and release.
3. **Killed process.** If the driver process is killed during a hold, the release code does not run. This was not tested.
4. **Not tested:**
   - Taps without a hold on phone still go through Playwright's mouse-style click, as in the original.
   - Holds on phone may trigger the browser's own long-press behaviour, such as a context menu.
   - The repo's existing driver tests and the TypeScript type check were not run.
   - Only Chromium, one viewport per device, and no scrolling during a hold were exercised.
