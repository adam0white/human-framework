## 1. The two posts

### Eko: an LLM agent left alone on an island (MIT)

- **What it is (confirmed, [arXiv 2610.07130](https://arxiv.org/abs/2610.07130), submitted 2026-10-05; [TNW](https://thenextweb.com/news/mit-claude-agents-virtual-island-play), 2026-10-19).** "Is this machine playing?" by Cloos, Norelli, Durbin, Andreas, Rus and Isola. Claude Code running Claude Opus 4.7 is the mind of a body on a simulated island with hills, twelve cubes, a rock and a ring. It sees a text list of objects, and it can move, jump, pick up, place and throw. Thirteen copies each ran 30 hours with no task. A `SOUL.md` file described the agent as curious and easily bored. The world reset hourly, while the agent's text-file notes persisted. Replays are at machineplaying.org.
- **What it did (confirmed, TNW).** The agents climbed hills, drew figures with blocks, invented games and wrote memorials. Almost all found a built-in rule (a hard-thrown rock makes new cubes). Six found a jump-throw trick the researchers did not know their world allowed. In a follow-up, experienced agents placed 10.3 objects on the Spire against 3.5 for fresh copies. Removing a useful technique from the notes made an agent worse; removing a false belief made it better.
- **What is novel.** The claim is that an untasked agent shows the four classic signs of play (self-made rules, repetition with variation, make-believe, goals pursued for their own sake), and that the play is useful: notes from play transfer to later tasks. Critics quoted by TNW (Yiu, Berkeley) say the paper shows play-like behaviour, not motivation. The authors concede role-play is possible.
- **Assumed, from TNW only.** TNW says OpenAI's Codex wrote the world's code from the team's description, which is how the unknown jump-throw rule got in. The arXiv abstract does not say this.
- **Sandboxing (confirmed, TNW).** In earlier runs without a locked-down sandbox, agents read the world's code, ran into parallel runs and worked out that they were in an experiment.

**How it relates to HF.** Eko and HF people are opposite designs.

| | Eko | HF person |
|---|---|---|
| Mind | An LLM, prompted by `SOUL.md` | A deterministic loop over plain-JSON state, no LLM (standing rule) |
| Inner life | Whatever the model writes in its notes | Needs, fatigue, attention, temperament, beliefs, ties, norms, habits, as owned state slices |
| Memory | Free text files the agent edits | Typed memories, gists and acquired-method evidence |
| Cost per day of life | Model tokens for every step | Local CPU only, no tokens (exact cost per workload not benchmarked here) |
| Replay | A recording | Exact, from seed and input log |

Three parallels are worth naming:

1. `SOUL.md` is a prose temperament. HF's temperament and agenda are the same idea as state that the loop reads every tick.
2. The unsandboxed agents reading the world's code is the failure our source-unread playtester rule ([playtester prompt](playtester-prompt.md)) already guards against. Eko's result is outside confirmation that the rule matters.
3. Experienced agents beating fresh ones, and false beliefs hurting, is what HF's acquired-method evidence and belief faculties model inside one person. Eko shows it in an LLM; HF could show it in many cheap people with exact replay. One caution: Eko's agent learns the world's rules by itself, while HF has no general motor planner or per-input rule learning. An HF person on Eko's island would explore only the affordances an adapter declares.

Any HF demo built on this puts an LLM agent **next to** HF people, never inside them. The actor loop stays LLM-free.

### Clairic: a typed-value extraction model on Workers AI (Cloudflare)

- **What it is (confirmed, [Cloudflare blog](https://blog.cloudflare.com/clairic-extraction-model/), Michelle Chen, 2026-10-19).** A preview "System One" model, `@cf/cloudflare/clairic`. You send a state (text plus up to four images) and a schema of typed fields: `text` (a span with offsets), `number`, `date`/`time`/`datetime`, `duration`, `list`, `estimate` (a distribution inside declared bounds) and `forecast` (one estimate per future step). It answers in one forward pass with no generated tokens. Each scalar comes with `confidence` and `p_null`; a missing value returns `null`. Estimates return a median and an 80% interval (p10 to p90).
- **Where it sits (confirmed).** Clairic extracts values, Clef (Cloudflare's decision model, which picks among listed options) decides, and an LLM writes text. In Cloudflare's claims test the cascade took 19.3 s against 61.7 s all-LLM (about 3.2x faster; secondary sources quote the same result as "69% faster") and cost about 49% less. Clairic's repair estimate was identical across runs; the LLM's varied.
- **Limits (confirmed, Cloudflare's own list).** Weak at multi-step arithmetic and aggregation across many rows ("let code do the math"). Estimates need evidence in the input. Calibration is "measured, not guaranteed". Forecasting is basic. The endpoint is an early checkpoint. Open weights are promised, not released.
- **Price and limits (confirmed, [model page](https://developers.cloudflare.com/workers-ai/models/clairic/)).** $0.10 per million input tokens; no output price is listed. Context window 65,536 tokens; up to four images of at most 4 MiB each. The blog post itself gives only the cascade cost.
- **What is novel.** A non-generative model for a job LLMs are routinely misused for: filling typed fields with calibrated uncertainty. Cloudflare reports repeatable outputs, and a `null` is offered where an LLM would invent a value. Cloudflare's own limits say answers are always well-formed but not necessarily correct, and an estimate can be returned on thin evidence, so `confidence` and `p_null` decide what a person checks. The benchmarks are the vendor's own small tests.
- **Note on the name.** The owner wrote "Clairic"; that is the product's spelling.

**How it relates to HF.** Clairic belongs in the lab, not in the games. It is the first Cloudflare model whose output shape matches what the lab already does by hand:

- **Ledger triage.** Playtester prose and opt-in run notes become typed rows (game, screen, complaint kind, quote span, severity), with spans that point back to the verbatim words. Today a Codex or Claude pass does this ([agent routing](agent-routing.md), T5). The test is agreement with rows a person has labelled, not with the last model pass.
- **Not calibration.** Clairic reading a quit time from prose is one more model's opinion. Calibration of the simulated testers needs observed human runs, including unfinished ones ([calibration](playtester-calibration-2026-10-20.md)).
- **A forecast cross-check.** HF's bodily forecast is deterministic. Clairic's `forecast` could read the same situation from prose; disagreement points at either a modelling gap or a bad description. This is a curiosity, not a priority.

Boundaries: nothing about qalb, nafs, fitra, ʿaql or the ruh goes through it (the no-quantification rule). It never runs inside the actor loop. Every call counts against the $5 Workers AI budget the owner approved on 2026-10-18.

## 2. AI-driven development practices in 2026

## 4. Which practices to adopt

### What we measured today

- **CI is fast.** The last eight `ci` runs on `main` before this commit passed, each in about 2.5 to 3.5 minutes wall time (3-way sharded tests plus a static job). The bench workflow already skips prose-only changes and never blocks.
- **The local gate is slow under load.** On 2026-10-20 at a load average near 100 (many agents on one machine), `npm run check` for this docs-only change took 702 s, and 5 of 1,583 tests failed, all on timeouts (60 s to 300 s), in long simulations (a fifty-year settlement, a multi-year Night Watch chronicle, Voice town runs). CI passed the same tests on the same code.
- **The deploy script repeats the gate.** `scripts/deploy.ts` runs `npm ci` and the full `npm run check` again, and does not check that CI passed for the commit it deploys.

These support a hypothesis, not a proven policy: the slow part is many full suites running at once on one machine, not CI.

### Recommendation

**Do not drop CI.** It takes three minutes, runs off the shared machine, and is the fast feedback that DORA associates with stability when AI raises change volume. **Do not loosen HF releases**: HF is the lab's published output, and a broken release reaches every game.

Cut duplicated work instead, with four lanes. A change takes the **strictest lane any of its files touches**, classified by what the change affects, not by directory.

| Lane | What it covers | Before push | Before it is public |
|---|---|---|---|
| **Gated** | `packages/human` and the HF release path; the lab Worker and anything privacy- or money-relevant; shared clients (`packages/lab-client`, `lab-kit`); lockfiles, CI workflows, deploy scripts | Full `npm run check` | Independent review, headless control, exact legacy continuation, CI green (unchanged) |
| **Delivery** | Game code that changes what the browser loads: asset paths, service workers, headers, `release.json` | Lint, typecheck, build, and a smoke check of the built page | CI green on the exact commit; a preview URL if risky |
| **Fast** | Game logic and polish inside one game | Lint, typecheck, and the tests related to the change (`vitest related`) | CI green on the exact commit |
| **Experiment** | Disposable research: a branch or scratch scene, no production deploy, no package release, no shared state | It builds and runs, plus one written falsifiable observation | Promoted into another lane, with that lane's checks, before it is kept |
| **Prose** | `docs/`, `research/`, Markdown only | Lint | CI runs on push |

Two changes make the lanes pay:

1. **Deploy checks CI instead of re-running it.** `scripts/deploy.ts` verifies that the `ci` check passed on the exact commit it deploys, then builds. The full local re-run is removed.
2. **Limit concurrent full suites on the lab machine.** One full suite at a time, queued; other agents use their lane's checks. Try this first: it may remove most of the pain on its own.

**How to tell whether it works.** For one week of lane commits, record the time from "change ready" to "usable revision on `main`" (local checks, CI queue, cancellations, repair work) and every defect that reached a live site. Compare with a baseline week of similar changes under today's rule. If time falls and escaped defects do not rise, keep it. If more than about one push in ten turns `main` red, the fast lane is too fast.

This changes a rule in AGENTS.md ("`npm run check` ... must pass before every commit") and the deploy script, so it is a **proposal for the owner**, not a change made here. This commit followed today's rule: the full suite ran once (702 s, 5 timeouts); the 7 timed-out files were rerun together (2 still timed out, 346 s) and the last 3 files passed when run one at a time. That small sequence is itself weak evidence for limiting concurrent suites first.

### Other practices

- **Keep routing by evidence.** The [agent routing](agent-routing.md) bake-off is better evidence for us than vendor routing claims. Redo it when a model changes.
- **Risk-tiered review, as Cloudflare describes.** Prose and game polish: one Codex pass. HF, Worker and shared-client code: Codex plus an Opus pass. This is mostly current practice; the proposal is to write it down.
- **Small batches.** One concern per commit and per agent. Agents produce large diffs, and review is the scarce part.
- **Agent-written property tests** in the gated lane (#6), **preview URLs** for risky game changes (#7), **enforced sandboxes** for source-unread testers (#8).

### What not to adopt

- **Agent teams as default infrastructure.** They are experimental, cost more tokens, and two agents editing one file overwrite each other, which is already our most common collision. Subagents with one owner per file are enough.
- **An LLM judge for taste.** Testers are evidence, not the target (owner, 2026-10-20). A judge scoring "fun" would pull games toward the bland middle the owner warned against.
