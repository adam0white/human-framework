## Executed result and narrow decision

At committed source **`b62fc0f6ff87bb32fc2aa0aba4d4d7276fcca928`**, both validators accept all **16 legal fixtures**. Their accepted physical worlds are identical. All nine changed snapshots still pass the actual full kernel validator; replay and local validation disagree in four prescribed cases:

| Changed snapshot | Source replay | Local invariants | What the difference establishes |
|---|---|---|---|
| Increase the idle player's bounded fatigue without changing paid receipts | Reject | Accept | Replay links current body to the specific window commands |
| Substitute a separately legal five-minute gathering world for a five-minute idle world from the same root | Reject | Accept | Aggregate-valid paid work can differ from recorded work |
| Move both the window and kernel's latest completed-cache time one minute earlier | Reject | Accept | Matching local receipt timestamps do not derive the actual completion minute |
| Reverse same-minute allocation/dispatch commands while retaining the previously valid physical world/window | Reject | Accept | An inclusive boundary alone cannot prove which same-minute operation came first |

Both reject the other three corrupted window cases: shifted pinned ferry deadline, duplicate cache ownership and a changed original Rain allocation prefix. The rival is therefore doing meaningful work beyond accepting anything the kernel accepts. Both **accept** the changed-body controls before the story window and six minutes after Return. The public host deliberately has no complete historical body replay claim there; the window journal must not be described as authenticating the entire camp's history.

The result supports a **specific finite-window integrity contract**: a source journal lets the importer establish that its retained entry, actual command order, derived completion times and current world agree. If the intended contract were only “load a physically and locally consistent current camp,” the faster snapshot rival is sufficient for these cases and a command journal is not required. These self-authored cases do not establish player benefit, general necessity, better human realism, or protection against an attacker editing both the world and its complete history coherently. Extra model-specific aggregate body bounds could reject some simple body changes without replay; this probe does not prove replay is the cheapest possible solution for every mismatch.

There was no outcome-driven correction or physics tuning: the first frozen rival and all first results are retained. The 16 valid cases include pre-entry, busy earned entry, imported introduction, paid idle/gather, a four-minute meal at the ferry and its paid continuation, rain/Return, three synthetic old Rain continuation phases, carried allocation/dispatch, newly completed cache, and one intentionally repetitive 500-command load. The latter is a bounded cold-load stress case, not typical measured human behavior. No original player export was read or copied.

## Cold-load and state costs

Each number below is the median of three independent `JSON.parse` + restore calls on Node 26.8.1, with fresh parsed input so the public trusted-object cache cannot bypass validation. Neither is an ordinary cached-book update measurement.

| Legal fixture | Journal commands / paid window minutes | Source replay | Local invariants |
|---|---:|---:|---:|
| Partial gathering | 3 / 5 | 2.90 ms | 0.81 ms |
| Partial meal at ferry | 4 / 90 | 20.48 ms | 0.75 ms |
| Ended at rain | 5 / 180 | 37.37 ms | 0.69 ms |
| Legacy Rain already-ended import | 0 new commands / retained old window | 0.86 ms | 0.53 ms |
| Repetitive journal | 500 / 100 | 117.66 ms | 0.96 ms |

The negative cost finding matters: even a five-command journal can replay 180 paid minutes, while an already-ended original Rain snapshot can validate without that new command replay. Current book caching reduces ordinary updates to roughly 1–4 ms, but the earlier roughly 627 ms five-slot/500-command cold restore remains a real load-time tradeoff. These machine timings are not phone/Safari performance claims.

Both validators consume the **same full saves** in this experiment. The 500-command save is 31,679 bytes; deleting only its command field would leave a 13,500-byte projection, saving 18,179 bytes. A five-command ended save is 12,839 bytes, versus a 12,704-byte projection: only 135 bytes differ. These projections are byte accounting only, not a compatible implemented public save format. The full root/current-world and temporal receipt obligations remain; deleting a journal alone does not remove them.

The private validator is **10,126 bytes / 117 nonblank lines**, with a 122,103-byte static import graph. The public story module is **17,503 bytes / 186 lines**, with a 129,480-byte graph. This is **not a net-source-size victory** for the rival: the public module also implements all actions, transitions and views, while the rival only validates. A complete alternative would retain or reimplement those host obligations. The rival also duplicates root mapping, deadline rules, prefix ownership, finish rules and minimum receipt spacing that must track future host changes. No second engine, public save version, package export or generic validator is promoted.
