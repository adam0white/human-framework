# Security review, H2 (HF 2.0), 2026-10-04

Scope: `git diff 73f063a..HEAD` (HEAD ff95cb5): `restore`/`migrate` and the optional slices added since (family, bonds, ambient, gists, yearbook, character, skill consolidation, `social.impressions`, `social.reserve`); Game 3 saves (`apps/site/src/watch/store.ts`, `worker.ts`, the shelf, "Take up again", season-backup fallback, scenario refusal); playtest export, import and replay in all three games; `apps/site/public/_headers` against the new features; secrets; dependencies. The live site was checked at c9c5f73 (`/release.json`), which differs from HEAD only by a findings note. Read-only review: nothing in source, tests or Cloudflare was changed.

Already decided in round 1 and not raised again: Google Fonts (rejected), HSTS in the zone and not in `_headers`, the CSP shape of 19c50d3, and playtest import validation (round-1 V6: `parsePlaytest`, `Object.hasOwn` in `migrate`, unknown top-level keys dropped by `restore`).

Threat model, unchanged: a static single-player site with no accounts, no backend and no secrets. Two inputs can come from someone else: (1) a playtest file or `?replay=` URL in Games 1–2, which is replayed from its seed and log and never loads the snapshot, and (2) a saved person passed to HF's public `restore` by any host. Game 3 has no import: its pages come from same-origin IndexedDB and are written only by its own worker. So the shipped site is not exposed to S1–S2. They are findings against HF 2.0's public `restore`, which round 1 treated as the boundary for untrusted saves.

## Findings

| ID | Sev | Status | Finding | Evidence | Fix |

| S1 | medium (library), not reachable on the site | **proven** | `restore` accepts a non-finite or huge `now`, and the next `tick` never returns. | `packages/human/src/person.ts:1664` checks only `typeof json.now !== 'number'`. `JSON.parse` turns `1e999` into `Infinity`, so a JSON file can carry it. Repro (scratch `probe.ts A2`, `probe3.ts big`): restore a fresh person's snapshot with `"now":-1e999`, then `tick(p, 600)`: killed by a 20 s timeout (exit 124). With `"now":1e18` and `tick(p, 1.1e18)`: also killed at 20 s. Once `now/60` passes 2^53, the grid `(Math.floor(p.now/seg)+1)*seg` (`person.ts:516`) rounds back to `p.now`, so the `while (p.now < now)` loop at `person.ts:513` stops advancing. With `"now":1e999` the person is frozen instead: every `tick`/`skip` becomes a no-op. | In `restore`: require `Number.isFinite(json.now)` and a domain bound (for example `Math.abs(now) <= 2**50`, about 2e9 years of minutes), else throw. Add a no-progress guard to `tick`'s loop (`if (end <= p.now) break` or throw) so a host passing a huge `now` cannot hang either. Add both cases to `migrate.test.ts`/the restore tests. |
| S2 | low | **proven** | Other scalar fields accepted by `typeof === 'number'` let non-finite values poison a restored person. `life.bornAt` is the worst case because it seeds the defaults. | `person.ts:1672` passes `life.bornAt` into `createPerson` before `fillFrom` runs. With `"bornAt":-1e999` the default is `-Infinity` too, so `fillFrom`'s non-finite fallback (`person.ts:1584`) puts the same `-Infinity` back. Repro `probe3.ts bornInf`: restored `bornAt -Infinity`. The run goes on, but the value serializes as `null`, so the next `restore` resets `bornAt` to 0 and the adult comes back as a newborn. The same typeof-only pattern appears for `nextDecision` (`:1688`), `will.command`/`lastCommand`, `affect.crisis`, `body.lastSleep`/`lastDowned`, `agenda.lapse`, `family.pregnancy.{conceivedAt,dueAt,seed}` (`family/family.ts:125-128`), `ambient.since` (`environment/environment.ts:93`) and `bonds.mourning.since` (checked with `num`, which is fine). Probes with ±1e999 in pregnancy, ambient, mourning, `character.experience` and `skillRetention` neither crashed nor left non-finite traits or values within 3 days lived plus a 2-year skip. | One shared `isNum` (already at `person.ts:1627`) for every scalar check in `restore` and in the slice sanitizers. Clamp `bornAt` to finite values ≤ `now` before building the defaults. |
| S3 | low | **proven** (timing) | `restore` does not enforce the caps that the live code keeps, so oversized arrays survive into later runs. | `memory.gists` is only filtered (`person.ts:1759`), but `GIST_DEFAULTS.maxGists` is 64 and `maxTags` is 6. `chronicleYears`, `trace`, `habits`, `social.impressions` and `bonds.courtships`/`marriages` are uncapped, and arrays are "taken whole" (`fillFrom`). Repro `probe.ts D`: 200,000 gists, `restore` 334 ms, then 3 days of `tick` 830 ms (about 5 ms normally). Bounded by the host's input size, so not a hang. | Truncate each array to its module's cap on restore (gists to `maxGists` by weight, tags to `maxTags`, years to the yearbook's horizon, impressions to their cap). Document the largest save `restore` is meant to accept. |
| S4 | low | proven by reading | Game 3 `load`: the `try` covers only `WatchRun.resume`. A page that parses but is malformed is never answered, and it replaces the running game. | `apps/site/src/watch/worker.ts:202-221`: `begin()` sets `run = next` and then calls `seasonMark`→`dayOfYear` on the new state, and `flush(true)` calls `buildFrame`. Both run inside `.then`, outside the `try` and outside `hostWorker`'s catch (`shared/worker-host.ts:28`). If `begin` throws, nothing posts `loaded`, so `actions.load` in `useWatch.ts:72-81` waits forever, the old run is already replaced, and every later `tick` throws into `error`. The season-backup fallback (`store.ts:147`) fires only when `readPage` returns null, not when the state is bad. `WatchRun` (`sim/run.ts:126-130`) checks only `scenario` and `seed`. Reachable only through shape drift without a `WATCH_SCENARIO_VERSION` bump, or a corrupted page. | Build and check the run before `begin`: in `resume`, require `log` to be an array and `state` to have finite `minute`/`year` and a known `phase`, and call `buildFrame(next.state, …)` once as a probe. Wrap the whole `.then` body so that any throw posts `loaded ok:false` and keeps the old run. A fake-indexeddb test in the `saves.test.ts` pattern can write a bad page and assert `ok:false`. |

## Suspected, not verified

- `validCharacter` (`person.ts:1612`) counts numeric values but does not check the trait and value keys. A `baseTraits` with wrong keys survived a 2-year skip with finite traits (`probe.ts E`), because `clamp` passes `NaN` bounds through, so traits then drift without their anchor band. This is a quality issue, not a crash. Checking the six trait and ten value keys by name would close it.
- Whether S4's stuck load leaves a visible message: `useWatch` has a worker `error` listener, but no timeout on `actions.load`. I did not run it in a browser.

## Recommended order

1. S1: finite and bounded `now` in `restore`, plus a no-progress guard in `tick` (S, with tests). This is the one finding a hostile save can turn into a hang in any HF host.
2. S2 and S3 with S1, in the same `restore` pass.
3. S4 before Game 3's next scenario bump, since shape drift is the likely way to reach it.
4. S5 and S6 are design notes for a future page or export import; there is nothing to do today.
