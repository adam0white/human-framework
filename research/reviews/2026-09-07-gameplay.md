No application, scenario, benchmark artifact or release was changed.

**Recommendation: keep the current recovery physics for now. Change the comparator and the next application before adding a penalty or another human faculty.** The current project is a useful inspectable scheduling laboratory. Its roadmap is careful about evidence, but completing its three iterations would still not demonstrate a reusable framework embedded in a distinct game. ## Priority findings

### 1. Recovery currently includes a controller responsibility

**Observed.** In `src/core/simulation.js:107–118`, a work/help request that exceeds capacity becomes full rest or eating. That fallback can consume shared food even when the scenario offers no eating action. The code explicitly supplies synthetic actions when the scenario does not provide recovery actions.

Focused example: use Solo with initial fatigue 0.10, hunger 0.98, and only its two work actions. Request work. Execution becomes `_eat`; food goes from 3 to 2, hunger from 0.98 to 0.47. No meal was requested or offered. This is valid under the present contract; it is not an implementation regression.

**Judgment.** Stopping impossible exertion and choosing how to spend another scarce resource are different responsibilities. A host game may have owned food, inaccessible food, fasting, an evacuation requiring supplies later, or a deliberate decision to preserve a ration. It cannot safely infer those choices from the fact that exertion is impossible. The framework must make the fallback policy explicit at the host boundary before integration. This is a more consequential issue than whether mandatory rest feels sufficiently expensive.

**Recommended next contract decision.** Preserve the 0.2 execution contract and historical replay. In the next host contract, physical resolution should report a blocked/partial attempt or required interruption; a declared controller chooses permitted recovery, with the host owning resource access and debit. Decide explicitly whether a known infeasible request is prevented by the interface, costs an attempted interval, or invokes a configured fallback. Never expose hidden actual capacity through free validation. These are alternatives to test, not approval to silently change current play.

### 2. The complaint about greedy work is partly correct, but an extra punishment is not established

**Observed.** Solo seed 7 after one precision-work action has fatigue 0.93 and hunger 0.29. From that same state, requesting precision work causes `_rest`; requesting rest causes `rest`. Both produce fatigue 0.46, hunger 0.33, progress 3 and food 3 after the same interval. The physical benefit is exactly equal. Repeated work requests therefore delegate upkeep to the resolver.

That does not mean greedy is optimal: earlier recovery can improve subsequent work chances and its timing changes finite-horizon outcomes. The independently reproduced 24-round result favors the simple recovery controller by 14 percentage points over greedy. The exploration also retains Solo's 18-round result, where greedy wins 17/100 versus planned 14 and Full 11 (`docs/recovery-design-exploration.md:17–30`).

**Judgment.** At an urgent deadline, accepting fatigue or failure risk can be sensible. A design that ensures cautious recovery always wins would eliminate a legitimate tradeoff. A local equality between compulsory and voluntary rest is not automatically an exploit; it becomes a product problem when a UI purports to require upkeep decisions but a single work button conveniently performs them all.

**Recommendation.** First compare the existing rules under normal and pressure workloads using stronger simple controllers. Keep the ordinary presets forgiving. A pressure variant is useful for a focused playtest, not a new proof of Full or a substitute for a real host game. Only test interruption cost when a specific game activity has an intelligible interruption consequence, such as abandoning a prepared operation. Name that consequence and give every controller the same rule. Do not choose a cost to produce the desired winner.

### 3. Full is a reactive utility policy; its failures should not be attributed to inadequate human physics

**Observed.** Work, rest and eating scores in `src/core/policy.js:17–28` do not read remaining target or deadline. Horizon appears only in the inspection term at lines 29–33. The implementation documentation acknowledges the absence of multistep planning.

Focused example: current Solo data with only target changed to 3 and horizon to 1, seed 7. Full rests, produces 0 and loses. The baseline requests precision work, produces 3 and wins. This one-seed example establishes the missing decision dependence; it is not a population comparison. The reason for preferring work at this terminal state can be stated without invoking recklessness: rest cannot finish the only remaining objective.

**Judgment.** Tightening a deadline measures compatibility between a reactive maintenance schedule and that deadline. It does not demonstrate that the Full policy deliberates about the deadline. An improvement attributed to the framework should survive comparison with a small task-aware controller that considers remaining work, time, feasible actions and food. Keep the current greedy controller as a deliberately limited diagnostic, but stop treating it as the principal product competitor.

A game's competing controller should also include a straightforward scripted task policy. The relevant question is whether the framework buys useful, controllable variation and lower authoring burden beyond such a policy—not whether a controller that never voluntarily eats can be defeated.

### 4. Four names do not yet expose four game problems

**Observed.** All presets use two work variants plus upkeep, one stationary scalar hazard, repeated independent attempts and one shared aggregate progress objective (`src/scenarios/index.js:11–80`). Commons adds continuous consumption; Solo removes social coupling. The resolver adds every successful output to the same progress variable, and checks success only after the whole round (`src/core/simulation.js:52–62,133–145`). There are no task dependencies, persistent repaired objects, navigation, distinct recipients, ownership or actor-specific objectives.

**Judgment.** These fixtures show kernel reuse within a family of scheduling problems. A player mostly learns work/recovery thresholds against stochastic throughput. Restyling another aggregate target will add little evidence that a real game can supply changing opportunities and use consequences. Likewise, a request/accept action that merely adds another progress bonus would not sufficiently resolve this limitation.

The roadmap's fixed-duration recovery and retention comparisons are useful mechanism experiments. They should not postpone a small distinct application until a larger theory is complete. Its current sequence needs a host-game acceptance gate, not simply more faculties.

### 5. The social mechanism and UI have not yet earned their prominence in ordinary play

**Observed.** The reported relationship ablation changes no objective outcome in all four presets (`docs/benchmark-report.md:60–72`). Help assigns a support increment without a recipient decision (`src/core/simulation.js:78–85`). Both actors share one victory condition; a command controls only one actor while the other uses the configured policy (`src/core/simulation.js:102–104`). The UI accurately explains that second point.

The UI shows numeric policy rank on every action card and explicitly announces the favored action (`web/app.js:249–262,302–312`). It also prominently displays trust, proficiency and condition estimates. These are useful laboratory instruments. They are not evidence that a first-time player can infer a good plan without being shown the policy's answer.

**Judgment.** The next social task needs another person who can want something incompatible with the player's immediate goal, whose response matters later. It should not award a social bonus simply for pressing Help. For ordinary playtests, default policy hints and arithmetic off, retaining action costs, estimated uncertainty and an optional explanation after a decision. Keep the research controls available. This is an experiment in comprehension, not a mandate to redesign the current laboratory.

## Smallest next playable application and sequencing

**First gate: one worker, two locations, one repair with real prerequisites.** Keep the host small and browser-delivered. For example, restore a pump before a scheduled departure: retrieve a particular part from storage, bring it to the pump and complete an operation that changes the pump's persistent state. Travel, inventory, operation availability, the departure and the repaired object belong to the game. The human component supplies only the capacities and state changes the game actually uses. Rest remains an available choice; do not add injury, emotion or detailed physiology to justify the premise.

The point is not another theme. The operation must become available because the part arrived, and the game must be able to use the repaired pump after the task. This tests an actual host boundary that the aggregate lab cannot test. Freeze a minimal contract after implementing this example, rather than designing a universal affordance system first. A native-engine port is unnecessary for this gate.

**Second gate, in the same application: one borrowed tool and one independent NPC.** Once the first gate works, give an NPC ownership of a needed tool and a conflicting upcoming job. The player may request a loan and promise to return it. The NPC can accept or refuse based on available evidence and their own current commitment. An alternative slower repair remains possible; cooperation should create a tradeoff, not a mandatory morality puzzle. A later operation makes return, refusal or nonperformance materially consequential. Do not infer dishonest intention from a failed attempt.

This requires a target, an independent response and an object/obligation outcome; add precisely those missing concepts when the host needs them. It does not require autobiographical memory, personality expansion, emotional appraisal, general planning or generated dialogue. Use a tiny explicit event record for the relevant prior exchange before claiming a general memory faculty.

**Sequencing judgment.** Host integration precedes social/cognitive expansion. A body-only two-location job is a sufficient integration gate, but it is insufficient evidence of the distinctive value of a broad human-behavior framework. The subsequent independent response is the smallest additional demand I would require before calling the application a convincing demonstration of that broader ambition. Scientific calibration can proceed as a separate narrowly bounded research task; it should not gate a mechanically useful host prototype unless the product is making an empirical claim.

This ordering is a design judgment. Two relevant primary precedents are modestly supportive: the [MDA paper](https://www.cs.northwestern.edu/~hunicke/MDA.pdf) argues for tracing system decisions through their resulting player experience; [Prom Week's own description](https://promweek.soe.ucsc.edu/2012/02/22/prom-weeks-social-exchanges/) separates the player's initiated exchange from a recipient's accept/reject decision, then chooses dialogue to express that result. Neither source proves that this particular pump/tool design will be enjoyable or validates its human model.

## Concrete acceptance gates

These are proposed project decisions, not scientific thresholds inferred from data.

| Gate | Evidence required before expanding |
|---|---|
| Recovery/control | The game documents who chooses fallback, who owns food, what consumes time and which observations permit a choice. A rejected exertion cannot silently invent access to a ration or an inaccessible rest action. Current 0.2 replay and Solo behavior remain available and unchanged. |
| Actual embedding | The host owns an object with at least two prerequisite states and changing available actions. The same exported human functions drive headless and browser play. Host inventory/time debits happen exactly once. No scenario-name conditionals enter a supposedly common human mechanism. |
| Meaningful choices | At least two feasible ways finish the same authored job with different costs/consequences, and at least one understood choice can fail. A player can describe what the next decision will change. A higher success count by itself does not pass this gate. |
| Comprehension | In a first round of five new-player sessions with policy hints hidden, at least four can state the objective, name one real tradeoff and explain an observed failure without opening omniscient diagnostics. Record confusion and guesses; this is a practical revision trigger, not an estimate for all players. |
| Comparison | Compare greedy, planned maintenance, a task-aware simple controller and the current Full policy using equal accessible information. Record completion by deadline, time, resource use, unfinished prerequisites and control interventions. Retain states where the simpler controller wins. Do not require Full to win if its retained value is a specific necessary representation rather than performance. |
| Independent NPC | Holding the material request constant, change one publicly available obligation/evidence item and obtain a traceable change in the NPC response. Both acceptance and refusal must produce playable continuations. Private intention must remain private, and unsuccessful performance must not establish insincerity. |
| Reuse and cuts | A second job with different object prerequisites is authored through the same boundary without retuning the shared body/learning rules or editing the first job. Record authoring time and workarounds. If most behavior remains custom scripts and the shared model adds no useful variation, keep the simpler controller and narrow the framework claim. |

## Cuts now

- No automatic recovery penalty, coefficients tuned to make Full win, new default deadline, additional reskinned scenario or native-engine migration from this review.
- No general emotion, episodic memory, developmental life course or expanded motive system before a host decision requires one and a simpler explanation has been tested.
- Do not make delayed retention calibration a prerequisite for the first host application. Preserve its scientific question on a separate track.
- Keep Solo Repair as the exact social null/control. The new independent interaction goes alongside it.
- Keep the laboratory's replay and causal inspection. For the new game, put the task, available choices and consequences first; use the laboratory view to investigate, not to supply the player's objective.

The strongest next evidence would be a small game that exposes an inconvenient integration requirement and then uses the resulting behavior. Another favorable Full-versus-greedy chart would be weaker evidence, even if statistically very precise within this simulator.
