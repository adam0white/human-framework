# Shared Promise comparison protocol

Registered 2026-09-08 before comparison controller implementation or new-host outcomes. Base `860aeb2`; core design dependency original `80adb4c`. This is a private deterministic software experiment. The ten authored cases below are not sampled people, a general planner, an optimum, a human explanation study, or evidence for a portable social faculty.

## Questions and arms

1. Does an explicit paid agreement achieve outcomes already possible through competent timed requests, and which extra choices or costs does it expose?
2. When does merely noticing the keeper's visibly running pump suffice? When does that rule fail because the keeper is still resting, has not started, or reneges?
3. Can a revision change a meaningful outcome while refused/interrupted/stale revisions retain old terms? Preserve communication overhead and unsuccessful agreements.

`original-fixed` uses unchanged Service Day 0.1.0 and only the prescribed keeper work. `original-timed` uses that exact old host plus accepted partner rest requests and explicit stops. The retained minute-41 control is reproduced exactly: keeper rest 41–47; partner rest 41–46, 46–51, 51–53; keeper pump 47–53; partner delivery 53–59. Its 12 paid partner rest minutes are a known prior exploratory result, not reserved evidence.

`direct-fixed`, `direct-timed`, `visible-pump`, and `agreement` all use the new Shared Promise physical rules, including permanent departure-slot commitment. `visible-pump` changes only Deniz's fallback decision: if the keeper is already doing the final pump section, inlet supply is ready, and that visible job ends no later than 57, defer cart choice until the observed pump completion. It does not forecast unseen future work, issue a promise, prevent interruption, pay discussion, or read private condition. All remaining autonomous recovery, invitation/terms consent, ownership, work and receiving-slot rules remain identical. The rival will be a private source-bound one-rule variant, not a public host option.

`agreement` uses the core's direct host record and real two-person, two-active-minute discussion. It receives no generic ledger or additional knowledge. Each command schedule is a deliberately prescribed intervention; policies see a detached public view and the preregistered scenario schedule, never raw host state or future outcomes. The runner may inspect exported saves only for accounting/replay validation, outside decision selection. Rejected actions are retained and execution proceeds to the next prescribed action; there is no outcome-based schedule search or silent retry. One non-advancing action is attempted per script entry.

Old/new hosts differ in available actions and departure interruption semantics. Their results are separate intervention comparisons, not a matched-physics causal estimate. Within the new host, all rival arms share physics, public information and actual resource/body costs. Partner rest substituted for holding is measured recovery, not discussion-equivalent exposure. No single weighted winner or aggregate social score is computed.

**E(t)** is the existing efficient gate route: keeper gate 0–6 and 6–12, salvage 12–20, meal 20–24, rest 24–30, then idle to t. Deniz independently repairs one pump section 24–30. The prefix is used at 30, 35 and 37. Its legal commands and actual carried condition must be checked; any correction is a dated protocol amendment before source freeze, with the originally specified case retained.

Terms below are `{pumpStartAt, readyBy, waitUntil, fallback}`. Safe S = `{39,45,45,'cart'}`. Risk R = `{47,53,53,'none'}`. An explicit promise describes future keeper actions; it does not perform them.
